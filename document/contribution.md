# Backend Contribution

Snapshot 프로젝트에서 담당한 백엔드 설계와 구현을 문제, 판단, 실행, 검증 순서로 정리했습니다.

## 담당 범위

| 영역 | 기여 내용 |
| --- | --- |
| API | 기획 세션, 사용자 답변, 이미지 업로드, 초안 생성·조회·선택·다운로드 |
| Database | 기획 정보, 이미지 정보, 초안 상태 테이블과 마이그레이션 |
| Model integration | REST 요청과 gRPC 계약 간 변환, 응답 식별자와 상태 검증 |
| State management | 기획 단계 전환과 필드 저장 규칙, 초안 생성 상태 관리 |
| Error handling | gRPC 오류 변환, 시스템 재시도와 사용자 재생성 분리 |
| Collaboration | Frontend·AI Model 담당자와 계약 조율 및 V1/V2 통합 테스트 |

## 1. 기획 단계 불일치 해결

### 상황

사용자가 챗봇 질문에 답하면 모델이 답변의 적절성을 판단하고 다음 기획 단계를 반환합니다. 연동 테스트 중 답변이 부적합해 같은 단계가 반환되었는데도 화면의 진행 표시가 다음 단계로 이동했고, 이후 요청의 `current_step`까지 잘못 저장되는 문제가 발생했습니다.

### 판단

화면 수정만으로는 같은 문제가 다시 발생했을 때 잘못된 상태가 DB와 모델에 전달될 수 있었습니다. 백엔드도 단계 전환의 유효성을 검증해야 서비스 전체의 기준을 하나로 유지할 수 있다고 판단했습니다.

### 실행

- 단계별로 갱신할 수 있는 필드를 제한했습니다.
- 현재 단계의 필수 데이터가 저장되기 전에는 단계를 유지했습니다.
- 현재 단계 유지 또는 정해진 다음 단계 이동만 허용했습니다.
- 허용되지 않은 단계가 들어오면 즉시 오류를 반환했습니다.
- Frontend는 직전 응답의 `next_step`을 다음 요청의 `current_step`으로 사용하도록 정리했습니다.

### 검증

정상 답변과 부적합 답변을 각각 입력하고 요청·응답 로그를 확인했습니다. 필수 정보가 충족된 경우에만 다음 단계로 이동하고, 부족한 경우에는 현재 단계가 유지되는 것을 확인했습니다.

## 2. 광고 방향별 입력 구조 개선

### 상황

객실, 분위기, 혜택 광고 3종을 하나의 숙소 장점 정보로 생성하자 입력이 짧을 때 결과가 비슷해졌습니다. 정보가 부족한 부분을 모델이 임의로 보완하면서 실제 숙소와 다른 광고가 생성될 가능성도 있었습니다.

### 판단

결과 이미지를 만든 뒤 문구만 고치는 방식보다 기획 단계에서 광고 방향별 정보를 충분히 받는 것이 우선이라고 판단했습니다.

### 실행

- 객실 광고는 숙소의 내외부 특징과 전망 정보를 사용했습니다.
- 분위기 광고는 원하는 무드와 색상 정보를 사용했습니다.
- 혜택 광고를 위해 `lodging_service` 필드와 질문 단계를 추가했습니다.
- DB 스키마, Alembic, API 스키마, Protobuf, gRPC 변환을 함께 수정했습니다.

### 검증

짧은 장점 정보만 입력한 경우와 객실 특징·분위기·혜택을 분리해 입력한 경우를 비교했습니다. 개선 후에는 세 광고가 각 방향의 정보를 구분해 반영하는 것을 확인했습니다.

## 3. 시스템 재시도와 사용자 재생성 분리

### 상황

광고 초안 3종 중 하나가 모델 또는 외부 서비스 오류로 실패했을 때 전체를 다시 생성하면 비용과 시간이 늘고, 사용자의 재생성 기회까지 소모될 수 있었습니다.

### 판단

사용자가 결과가 마음에 들지 않아 다시 요청하는 경우와 시스템이 정상 결과를 만들지 못한 경우는 서로 다른 사건이므로 같은 정책을 적용하면 안 된다고 판단했습니다.

### 실행

- 최초 생성 실패 시 실패한 초안만 같은 `draft_id`로 재시도했습니다.
- 성공한 초안은 다시 생성하지 않았습니다.
- 시스템 재시도는 사용자 재생성 횟수에 포함하지 않았습니다.
- 1차 초안 3종이 완료된 뒤에만 사용자 재생성을 허용했습니다.
- 2차 초안 3종이 모두 완료되면 재생성 사용 상태를 확정했습니다.

### 검증

일부 초안 실패와 전체 성공 상황을 나누어 테스트했습니다. 실패한 항목만 재요청되고 시스템 재시도 뒤에도 사용자 재생성 기회가 유지되는 것을 확인했습니다.

## 4. 모델 응답과 이미지 검증

모델 서버 응답의 `request_id`, `session_id`, `state_revision`, `current_step`을 원래 요청과 비교해 다른 세션이나 오래된 상태가 반영되지 않도록 했습니다. 생성 이미지에는 파일 형식과 `1080 × 1350` 규격 검사를 적용하고, 세션과 초안 ID를 기준으로 저장 경로를 만들었습니다.

## 협업 방식

연동 문제는 한 파트의 코드만 보고 판단하지 않고 화면 공유와 요청·응답 로그를 함께 확인했습니다. 백엔드에서 보장할 규칙과 Frontend·AI Model에서 수정할 계약을 구분해 합의한 뒤 각 파트의 변경을 다시 연결해 검증했습니다.

## 배운 점

기능 구현 속도만큼 중요한 것은 서비스가 어떤 상태를 신뢰할지 정하는 일이라는 점을 배웠습니다. 입력 구조, 단계 전환, 재시도 정책처럼 사용자는 직접 보지 못하는 규칙이 결과의 정확성과 사용 경험을 결정했습니다. 또한 AI 도구와 함께 코드를 작성하더라도 요청·응답 로그와 테스트 결과를 직접 확인해야 자신의 판단으로 코드를 설명하고 개선할 수 있다는 기준을 세웠습니다.
